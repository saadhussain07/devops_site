Terraform lets you define your entire cloud infrastructure as code. Instead of clicking through the AWS console and forgetting what you did, everything is versioned, reviewable, and repeatable.

Installation & Setup

# Install Terraform (macOS)
brew install terraform

# Verify
terraform version

# Configure AWS credentials
aws configure

Project Structure

my-infra/
├── main.tf          # Core resources
├── variables.tf     # Input variables
├── outputs.tf       # Output values
├── terraform.tfvars # Variable values
└── versions.tf      # Provider versions

Provision a VPC + EC2 Instance

# versions.tf
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = var.region
}

# main.tf
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
  tags = { Name = "devops-hub-vpc" }
}

resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
  map_public_ip_on_launch = true
}

# Look up the latest Amazon Linux 2023 AMI instead of hardcoding an ID
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-2023*-x86_64"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.public.id
  tags = { Name = "web-server" }
}

The Terraform Workflow

# Initialise — download providers
terraform init

# Preview changes
terraform plan

# Apply changes
terraform apply

# Destroy resources
terraform destroy

Always review terraform plan output before applying. It shows exactly what will be created, modified, or destroyed.

Variables and outputs

# variables.tf
variable "region" {
  type    = string
  default = "eu-west-1"
}

variable "instance_type" {
  type        = string
  default     = "t3.micro"
  description = "EC2 size for the web server"
}

# outputs.tf
output "instance_id" {
  value = aws_instance.web.id
}

# terraform.tfvars
region = "eu-west-1"

Remote state with locking

By default, state lives in a local terraform.tfstate file. That breaks as soon as two people or a CI job are involved. Store it in S3 instead; Terraform 1.10+ can lock it natively, with no DynamoDB table needed:

terraform {
  backend "s3" {
    bucket       = "yourname-terraform-state"   # create once, with versioning on
    key          = "dev/network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
  }
}

After adding a backend, run terraform init -migrate-state to move the existing state.

Modules: write once, reuse everywhere

modules/
└── web/
    ├── main.tf       # resources
    ├── variables.tf  # inputs
    └── outputs.tf    # outputs

# envs/dev/main.tf
module "web" {
  source        = "../../modules/web"
  instance_type = "t3.micro"
}

# envs/prod/main.tf
module "web" {
  source        = "../../modules/web"
  instance_type = "m7g.large"
}

For common building blocks, the community modules (e.g. terraform-aws-modules/vpc/aws) are well tested. Pin their versions.

Terraform in CI

terraform fmt -check -recursive
terraform init -input=false
terraform validate
terraform plan -input=false -out=tf.plan     # post this output on the PR
# after review and merge:
terraform apply -input=false tf.plan

Add tflint and a misconfiguration scanner (trivy config or checkov) to catch open security groups and unencrypted storage before they reach AWS.

Clean up: run terraform destroy when you finish experimenting, and set an AWS Budget alert. Forgotten NAT gateways and load balancers are the most common surprise bills.
