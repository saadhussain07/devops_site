Site Reliability Engineering (SRE) is what happens when you treat operations as a software problem. It gives teams a shared, numerical answer to the question that causes most dev-vs-ops arguments: how reliable is reliable enough? This guide covers SLIs, SLOs, error budgets, alerting, incidents and toil, with formulas and queries you can use straight away.

Why 100% is the wrong target

Users can't tell 99.99% from 100%: their own Wi-Fi and phones fail far more often than that. Each extra "nine" costs a lot more engineering and slows feature work. SRE picks a target that keeps users happy and spends the rest of the reliability "budget" on shipping.

SLI, SLO, SLA

  • SLI (indicator): a measurement of user experience, usually good events ÷ valid events. Example: the proportion of HTTP requests that return non-5xx in under 300 ms.
  • SLO (objective): the target for an SLI over a window. Example: 99.9% of requests are good, over 30 days.
  • SLA (agreement): a contract with customers, with consequences. Always looser than your SLO, so you get warned before you breach it.

Good SLIs measure what users feel, as close to them as possible (at the load balancer, or with synthetic probes), not CPU or memory.

Error budgets

The error budget is 1 − SLO. With a 99.9% SLO and 10 million requests a month, you can "spend" 10,000 failed requests.

  • Budget remaining: ship features, run experiments, take calculated risks.
  • Budget exhausted: freeze risky launches and spend engineering time on reliability until it recovers.

Agree this error budget policy with product owners in advance. Then reliability decisions are driven by data rather than by whoever argues loudest during an outage.

Measuring SLIs with Prometheus

# Availability SLI: share of requests that were NOT 5xx over 30 days
sum(rate(http_requests_total{job="api", code!~"5.."}[30d]))
  /
sum(rate(http_requests_total{job="api"}[30d]))

# Latency SLI: share of requests faster than 300 ms
# (needs a histogram bucket at le="0.3")
sum(rate(http_request_duration_seconds_bucket{job="api", le="0.3"}[30d]))
  /
sum(rate(http_request_duration_seconds_count{job="api"}[30d]))

# Error budget remaining (1 = untouched, 0 = spent), for a 99.9% SLO
1 - (
  (1 - (sum(rate(http_requests_total{job="api", code!~"5.."}[30d]))
        / sum(rate(http_requests_total{job="api"}[30d]))))
  / (1 - 0.999)
)

In practice, use recording rules, or a generator like Sloth or Pyrra, so these long-window queries stay cheap.

Alert on burn rate, not thresholds

Burn rate is how fast you're spending the budget. A burn rate of 1 uses exactly the whole budget over the SLO window; 14.4 uses 2% of a 30-day budget in one hour. The multi-window, multi-burn-rate approach from the Google SRE Workbook pages for fast burns and opens tickets for slow ones:

# Fast-burn page for a 99.9% SLO (error budget = 0.001)
(
  sum(rate(http_requests_total{job="api",code=~"5.."}[1h]))
    / sum(rate(http_requests_total{job="api"}[1h])) > (14.4 * 0.001)
)
and
(
  sum(rate(http_requests_total{job="api",code=~"5.."}[5m]))
    / sum(rate(http_requests_total{job="api"}[5m])) > (14.4 * 0.001)
)

The short window makes the alert resolve quickly once the problem stops. The long window stops brief blips from paging anyone.

Incident response

  1. Detect: from SLO alerts, ideally before customers notice.
  2. Declare and assign roles: an Incident Commander coordinates, an Ops lead fixes, and a Comms lead updates stakeholders and the status page.
  3. Mitigate first: roll back, fail over, scale up, disable a feature flag. Root cause can wait.
  4. Communicate on a fixed cadence (e.g. every 30 minutes), even if nothing has changed.
  5. Resolve and confirm the SLIs have recovered.
  6. Learn: hold a blameless postmortem.

Blameless postmortems

People rarely cause incidents on their own; systems allow them. A postmortem asks how the system let this happen, not who did it. If people fear blame, they hide information and the same failure comes back.

## Incident: API 5xx spike, 2026-03-14
Impact:     18% of requests failed for 42 min; ~3,100 users affected; 31% of monthly error budget used
Detection:  Fast-burn SLO page at 14:07 (6 min after start)
Timeline:   14:01 deploy v2.31 → 14:07 page → 14:15 rollback started → 14:43 recovered
Root cause: Connection pool size cut from 50 to 5 in a config refactor; no load test caught it
What went well:     Alert fired fast; rollback was one command
What went poorly:   Rollback took 28 min because the old image had been garbage-collected
Action items:
  - [ ] Add a config validation test for pool sizes          (owner: @dev-a, due 03-21)
  - [ ] Keep the last 10 release images in the registry       (owner: @ops-b, due 03-18)
  - [ ] Add a pre-prod load test to the release pipeline      (owner: @sre-c, due 04-01)

Toil and automation

Toil is manual, repetitive, automatable work that grows with the service and has no lasting value: restarting a stuck job, rotating a certificate by hand, approving routine access requests. Google SRE teams cap toil at about 50% of their time and use the rest to engineer it away.

A simple habit: keep a toil log for two weeks, rank the entries by time × frequency, and automate the top one.

Other SRE practices worth knowing

  • Capacity planning: forecast from growth trends; load-test before launches.
  • Chaos engineering: inject failures in a controlled way (LitmusChaos, Chaos Mesh, AWS FIS) to test your assumptions.
  • Release engineering: canaries, feature flags and fast rollback. See GitOps with Argo CD.
  • DORA metrics: measure delivery performance alongside reliability. See DORA Metrics Explained.
