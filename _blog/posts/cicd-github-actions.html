GitHub Actions is one of the most powerful and beginner-friendly CI/CD tools available today. It's built directly into GitHub — no external servers, no plugins to manage. In this guide, you'll build a complete pipeline from scratch.

How GitHub Actions Works

Workflows are defined in YAML files inside .github/workflows/ in your repository. They are triggered by events — pushes, pull requests, schedules, and more.

Your First Workflow

# .github/workflows/ci.yml
name: CI Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

      - name: Build
        run: npm run build

Adding Docker Build & Push

  docker:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: myuser/myapp:${{ github.sha }}

Tip: Never hardcode credentials. Add secrets in GitHub → Settings → Secrets and variables → Actions.

Key GitHub Actions Concepts

  • Workflow — the YAML file defining your automation
  • Job — a set of steps that run on the same runner
  • Step — a single task (run a command or use an action)
  • Action — reusable unit from the Actions Marketplace
  • Runner — the machine that executes your workflow
  • Secrets — encrypted variables for credentials

Speed it up: caching and parallel jobs

Jobs run in parallel unless you link them with needs:. A matrix runs the same job across versions or platforms:

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm          # caches ~/.npm keyed on package-lock.json
      - run: npm ci
      - run: npm test

Docker builds can reuse layers between runs through the GitHub Actions cache:

      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/you/app:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Least-privilege permissions

Every workflow gets a GITHUB_TOKEN. Restrict it to what the workflow needs:

permissions:
  contents: read
  packages: write      # only if pushing to GHCR
  id-token: write      # only if using OIDC to a cloud

Deploy to the cloud without stored keys (OIDC)

Instead of saving AWS access keys as secrets, let GitHub issue a short-lived token that AWS trusts:

  deploy:
    needs: docker
    runs-on: ubuntu-latest
    environment: production         # can require manual approval
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy
          aws-region: eu-west-1
      - run: aws sts get-caller-identity

In AWS, create an IAM OIDC provider for token.actions.githubusercontent.com, and a role whose trust policy only allows repo:you/app:environment:production.

Environments and approvals

GitHub Environments (Settings → Environments) add required reviewers, wait timers, branch restrictions and environment-specific secrets. A job with environment: production pauses until someone approves it, which gives you continuous delivery with a human gate.

Reusable workflows

When several repos share the same pipeline, define it once:

# .github/workflows/build.yml in a shared repo
on:
  workflow_call:
    inputs:
      image: { type: string, required: true }

# caller repo
jobs:
  build:
    uses: your-org/ci-templates/.github/workflows/build.yml@v1
    with:
      image: ghcr.io/your-org/api
