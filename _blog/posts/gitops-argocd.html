In a traditional pipeline, CI runs kubectl apply or helm upgrade against your cluster. That means CI holds cluster-admin credentials, and nothing notices when someone changes the cluster by hand. GitOps flips this around: Git holds the desired state, and an agent inside the cluster continuously makes reality match it. Argo CD is the most popular such agent.

The four GitOps principles

  1. Declarative: the whole system is described as desired state (YAML, Helm, Kustomize).
  2. Versioned and immutable: that state lives in Git, with full history and review.
  3. Pulled automatically: an agent pulls changes from Git. Nobody pushes to the cluster.
  4. Continuously reconciled: the agent detects drift and corrects it.

What you get: every change is a reviewed commit, rollback is git revert, the audit trail comes for free, and CI no longer needs cluster credentials.

Repository layout

Keep application code and deployment configuration in separate repos, or at least separate folders. That way a config change doesn't trigger an app build, and access can be controlled separately.

gitops/
├── apps/                    # one Argo CD Application per app+env (app-of-apps)
│   ├── api-dev.yaml
│   └── api-prod.yaml
└── services/
    └── api/
        ├── base/            # shared manifests
        │   ├── deployment.yaml
        │   ├── service.yaml
        │   └── kustomization.yaml
        └── overlays/
            ├── dev/         # replicas: 1, image tag bumped by CI
            │   └── kustomization.yaml
            └── prod/        # replicas: 3, promoted by PR
                └── kustomization.yaml

Install Argo CD

kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# initial admin password
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d; echo

kubectl -n argocd port-forward svc/argocd-server 8080:443
# open https://localhost:8080 (user: admin)

For anything beyond a lab, install it with the official Helm chart, pin the version, and set up SSO instead of the admin user.

Your first Application

An Application tells Argo CD where to read from and where to deploy to:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-dev
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/you/gitops
    targetRevision: main
    path: services/api/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: api-dev
  syncPolicy:
    automated:
      prune: true       # delete resources removed from Git
      selfHeal: true    # revert manual changes in the cluster
    syncOptions:
      - CreateNamespace=true

Apply it once with kubectl apply -f apps/api-dev.yaml. From then on, every commit to services/api/overlays/dev is deployed automatically.

Sync status and health

  • Synced / OutOfSync: does the live state match Git?
  • Healthy / Progressing / Degraded: are the resources actually working? (e.g. whether the Deployment has rolled out all its replicas)
argocd app list
argocd app get api-dev
argocd app diff api-dev        # what would change
argocd app sync api-dev        # manual sync (for apps without auto-sync)
argocd app history api-dev

Connecting CI to GitOps

CI's job ends at "build, test, push the image, and update Git". Argo CD handles the deployment.

# .github/workflows/release.yml (in the APP repo, after the image push step)
      - name: Bump image tag in gitops repo
        env:
          GH_TOKEN: ${{ secrets.GITOPS_TOKEN }}   # fine-grained token, gitops repo only
        run: |
          git clone https://x-access-token:${GH_TOKEN}@github.com/you/gitops.git
          cd gitops/services/api/overlays/dev
          kustomize edit set image api=ghcr.io/you/api:${{ github.sha }}
          git -c user.name=ci -c user.email=ci@example.com commit -am "api: deploy ${{ github.sha }} to dev"
          git push

Promoting to production is then a pull request that copies the tested tag into overlays/prod. A human reviews and merges it. If you'd rather not have CI write to Git at all, Argo CD Image Updater can watch the registry instead.

Scaling up: app-of-apps and ApplicationSets

Writing one Application per service per environment gets repetitive. Two patterns help:

  • App of apps: one root Application points at the apps/ folder and creates all the others.
  • ApplicationSet: generates Applications from a template, e.g. one per folder or one per cluster.
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: services-dev
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - git:
        repoURL: https://github.com/you/gitops
        revision: main
        directories:
          - path: services/*/overlays/dev
  template:
    metadata:
      name: '{{index .path.segments 1}}-dev'
    spec:
      project: default
      source:
        repoURL: https://github.com/you/gitops
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{index .path.segments 1}}-dev'
      syncPolicy:
        automated: { prune: true, selfHeal: true }
        syncOptions: [CreateNamespace=true]

Secrets in GitOps

Never commit plain Kubernetes Secrets (base64 is not encryption). Choose one of:

  • External Secrets Operator: Git holds a reference, and the operator fetches the value from AWS Secrets Manager, Vault, etc. (the usual choice in the cloud).
  • Sealed Secrets: encrypt with the cluster's public key, then commit the ciphertext.
  • SOPS with KMS/age, decrypted by a plugin at sync time.

Progressive delivery with Argo Rollouts

Argo CD deploys whatever is in Git. Argo Rollouts controls how it rolls out: canary steps, traffic shifting, and automated analysis against Prometheus metrics that aborts and rolls back on its own.

strategy:
  canary:
    steps:
      - setWeight: 10
      - pause: { duration: 5m }
      - analysis:
          templates: [{ templateName: success-rate }]
      - setWeight: 50
      - pause: { duration: 10m }

Common pitfall: with selfHeal on, the HPA and Argo CD fight over spec.replicas. Remove replicas from the Deployment manifest when you use an HPA, or add an ignoreDifferences entry for that field.
