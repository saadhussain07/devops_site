Almost everything in DevOps runs on Linux: CI runners, containers, Kubernetes nodes and cloud VMs. You don't need to be a kernel hacker, but you do need to be fast and confident at the command line. This guide covers the commands and concepts you'll use every week, in the order you'll need them.

Practise as you read: run an Ubuntu VM with multipass launch --name lab, use WSL2 on Windows, or run a throwaway container: docker run -it --rm ubuntu:24.04 bash.

The filesystem layout

Linux has a single tree starting at /. The directories you'll visit most:

PathWhat lives there
/etcSystem and service configuration (/etc/nginx, /etc/ssh/sshd_config)
/var/logLog files (and journalctl for systemd services)
/var/libApplication state, e.g. /var/lib/docker
/home, /rootUser home directories
/usr/bin, /usr/local/binInstalled programs
/tmpTemporary files, often cleared on reboot
/proc, /sysVirtual filesystems exposing kernel and process information

Navigating and finding things

pwd                         # where am I?
ls -lah                     # long list, hidden files, human sizes
cd -                        # jump back to the previous directory
find /var/log -name "*.log" -mtime -1      # logs modified in the last day
find . -type f -size +100M                 # big files under here
which nginx; type ll        # where does a command come from?
tree -L 2                   # directory overview (apt install tree)

Reading and searching text

Most DevOps debugging is reading logs and config. Learn these until they're muscle memory:

less /var/log/syslog        # page through (/ to search, G for end, q to quit)
tail -f /var/log/nginx/access.log          # follow a log live
tail -n 100 app.log | grep -i error
grep -rn "listen" /etc/nginx/               # recursive, with line numbers
grep -v '^#' sshd_config | grep -v '^$'     # strip comments and blank lines

# count requests per status code in an nginx access log
awk '{print $9}' access.log | sort | uniq -c | sort -rn

# top 10 client IPs
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# find and replace in place (keep a .bak backup)
sed -i.bak 's/old-host/new-host/g' config.yaml

Users, groups and permissions

Every file has an owner, a group and three permission sets: user, group and others. Each set has read (4), write (2) and execute (1).

ls -l deploy.sh
# -rwxr-x--- 1 deploy ops 1.2K deploy.sh
#  └u┘└g┘└o┘   owner  group

chmod 750 deploy.sh         # rwx for owner, r-x for group, nothing for others
chmod +x script.sh          # add execute for everyone
chown deploy:ops deploy.sh  # change owner and group
sudo useradd -m -s /bin/bash deploy
sudo usermod -aG docker deploy   # add to a group (log out and in to apply)
id deploy                    # show uid, gid and groups

Never fix a permission error with chmod 777. Work out which user the process runs as (ps -o user= -p <pid>) and give that user the minimum access it needs.

Processes and resources

ps aux --sort=-%mem | head   # top memory consumers
top                          # or htop: live view (press P for CPU, M for memory)
pgrep -a python              # find processes by name
kill <pid>                   # ask nicely (SIGTERM)
kill -9 <pid>                # force (SIGKILL), last resort
free -h                      # memory (look at "available", not "free")
df -h                        # disk space per filesystem
du -sh /var/* | sort -h      # what's using the space?
uptime                       # load averages for 1, 5 and 15 minutes

A load average higher than your CPU count (nproc) means work is queuing. If the load is high but CPU usage is low, processes are usually waiting on disk or network I/O.

Services with systemd

Modern distributions use systemd to start and supervise services.

systemctl status nginx
sudo systemctl restart nginx
sudo systemctl enable --now nginx      # start now and on every boot
systemctl list-units --failed
journalctl -u nginx -f                 # follow a service's logs
journalctl -u nginx --since "1 hour ago" -p err

Running your own app as a service takes one small unit file:

# /etc/systemd/system/myapp.service
[Unit]
Description=My API
After=network-online.target
Wants=network-online.target

[Service]
User=myapp
WorkingDirectory=/opt/myapp
EnvironmentFile=/etc/myapp/env
ExecStart=/opt/myapp/bin/server --port 8080
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now myapp

Networking from the shell

ip a                          # interfaces and IPs
ip route                      # routing table
ss -tlnp                      # which processes listen on which TCP ports
curl -v https://example.com   # full request/response, including TLS
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com
dig +short example.com        # DNS lookup
nc -zv db.internal 5432       # is the port reachable?

For more on how these fit together, read Networking Fundamentals for DevOps.

SSH like a professional

ssh-keygen -t ed25519 -C "you@example.com"
ssh-copy-id deploy@server
ssh -i ~/.ssh/id_ed25519 deploy@server

# ~/.ssh/config: then just run "ssh web1"
Host web1
  HostName 203.0.113.10
  User deploy
  IdentityFile ~/.ssh/id_ed25519

# copy files
scp app.tar.gz web1:/tmp/
rsync -avz --delete ./dist/ web1:/var/www/app/

# reach a private database through a bastion
ssh -L 5432:db.internal:5432 web1

On servers, disable password logins (PasswordAuthentication no) and root login (PermitRootLogin no) in /etc/ssh/sshd_config.

Bash scripting essentials

Start every script with this header. It catches most of the bugs that make automation dangerous:

#!/usr/bin/env bash
set -euo pipefail      # exit on error, on unset vars, and on failures inside pipes
IFS=$'\n\t'

log() { printf '%s %s\n' "$(date -u +%FT%TZ)" "$*" >&2; }

usage() { echo "usage: $0 <environment>" >&2; exit 1; }
[[ $# -eq 1 ]] || usage
ENV=$1

case "$ENV" in
  dev|staging|prod) ;;
  *) usage ;;
esac

tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT          # always clean up, even on failure

for svc in api worker; do
  log "deploying $svc to $ENV"
  if ! curl -fsS "https://$svc.$ENV.example.com/health" >/dev/null; then
    log "health check failed for $svc"
    exit 1
  fi
done
  • Quote your variables ("$var") so spaces don't split them.
  • Use [[ ... ]] for tests, and $(...) for command substitution.
  • Run shellcheck script.sh. It finds real bugs in seconds.

Scheduling: cron and systemd timers

crontab -e
# m  h  dom mon dow  command
*/5  *  *   *   *    /opt/scripts/healthcheck.sh >> /var/log/health.log 2>&1
0    2  *   *   *    /opt/scripts/backup.sh

systemd timers are the modern alternative. Their logs go to the journal, they can catch up on runs missed while the machine was off, and systemctl list-timers shows when each one next runs.
