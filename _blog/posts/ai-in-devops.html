AI coding assistants and LLM agents are now part of everyday engineering work. In DevOps they are genuinely useful for some jobs and dangerous for others. This guide covers where they help today, where they don't, and the guardrails that let you use them safely on real infrastructure.

Generating infrastructure code safely

An LLM can produce a convincing Terraform module that opens 0.0.0.0/0 on port 22, or uses a deprecated provider argument. Treat AI output like a pull request from a fast but junior colleague:

  1. Give context: provider versions, naming conventions, existing modules, and your constraints (e.g. "private subnets only, encrypted at rest, tags required").
  2. Run the same gates as human code: terraform fmt/validate, tflint, checkov or trivy config, kubeconform, shellcheck.
  3. Read the plan: terraform plan is the ground truth, whatever the prose explanation says.
  4. Test in a sandbox account or cluster before anything reaches production.
# A practical review loop for generated IaC
terraform fmt -check -recursive
terraform validate
tflint --recursive
trivy config .            # misconfiguration scan (open SGs, unencrypted storage…)
terraform plan -out=tf.plan && terraform show -json tf.plan | jq '.resource_changes[] | {address, actions: .change.actions}'

AI in the CI/CD pipeline

Common patterns teams adopt:

  • AI PR review as a non-blocking check that comments on risky diffs, missing tests or secrets.
  • Failure summaries: when a job fails, an LLM posts a short "what broke and the likely fix" comment, so nobody has to scroll through logs.
  • Agentic fixes: a coding agent proposes a commit for a failing test or a dependency bump. It still goes through the normal pipeline and human approval.

Prompt injection is real: PR descriptions, issue comments, logs and even dependency READMEs can contain text crafted to steer an AI agent. Give agents that read untrusted input no secrets and no write access to protected branches or production.

Agents, tools and MCP

An agent is an LLM in a loop that can call tools: run kubectl get, query Prometheus, read a runbook, open a ticket. The Model Context Protocol (MCP) is an open standard for exposing such tools and data sources to AI applications in a consistent way. Many platforms (Kubernetes, cloud providers, observability tools, Git hosts) now ship MCP servers.

Design tool access the same way you design IAM:

  • Read-only by default. Investigation tools (get, describe, logs, PromQL queries) cover most of the value.
  • Narrow write tools such as "restart deployment X in namespace Y" or "scale within min/max", not a raw shell or kubectl apply.
  • Human approval for anything that changes production, with the agent's reasoning and proposed command shown.
  • Audit everything: every tool call is logged with who or what triggered it.
  • Separate credentials: the agent's identity has its own tightly scoped role, never a human's admin token.

AIOps: AI for incident response

AIOps applies ML and LLMs to operations data. A typical multi-agent setup:

Alert fires (Prometheus / Alertmanager)
   │
   ▼
Triage agent ── reads: alert, recent deploys, SLO burn rate
   │
   ├─► Metrics agent  ── PromQL: error rate, latency, saturation by pod/node
   ├─► Logs agent     ── Loki: error patterns around the start time
   └─► Traces agent   ── Jaeger/Tempo: slowest spans, failing dependency
   │
   ▼
Root-cause hypothesis + evidence + suggested runbook action
   │
   ▼
Human approves → guarded action (rollback / scale / restart) → verify SLIs recover

The value isn't magic root-cause detection. It's compressing the first 15 minutes of an incident, the gathering of context, into seconds, while humans keep the decisions. Read more about this architecture on the AIOps page.

MLOps in one section

If your team ships ML models, the DevOps principles carry over with a few additions:

  • Version data and models, not just code (DVC, MLflow model registry, artifacts in object storage).
  • Pipelines for training (Kubeflow, Argo Workflows, managed services) as well as for deployment.
  • Serving with autoscaling GPUs and specialised inference servers (vLLM, KServe, Triton).
  • Monitoring for model quality and data drift, not only latency and errors.
  • Cost control: GPUs are expensive, so track utilisation, batch requests, and right-size the model.

A sensible adoption path

  1. Use an AI assistant in your editor and terminal for drafts and explanations, and review everything.
  2. Add non-blocking AI PR review and CI failure summaries.
  3. Give a read-only investigation agent access to metrics, logs and runbooks.
  4. Only then automate narrow, reversible actions, behind approval and with full audit logs.

Skills still matter: AI makes strong engineers faster, but you can only judge its output if you understand Linux, networking, Kubernetes and IaC yourself. Use the roadmap and projects to build that foundation.
