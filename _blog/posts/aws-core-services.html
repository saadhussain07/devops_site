AWS has over 200 services, but a DevOps engineer uses about fifteen of them daily. This guide maps those core services to the jobs they do, shows how they fit together in a standard architecture, and covers the security and cost habits that keep you out of trouble.

Before you touch anything: turn on MFA for the root user and then stop using root. Create an AWS Budget with an email alert (say, $10/month), and use an IAM Identity Center user or role for daily work.

Global infrastructure

  • Region (e.g. eu-west-1): a geographic area. Data stays in the region unless you move it.
  • Availability Zone (e.g. eu-west-1a): one or more isolated data centres within a region. Spread across at least two AZs for high availability.
  • Edge locations: CloudFront and Route 53 points of presence close to users.

IAM: the most important service

Every AWS API call is authorised by IAM. The key concepts:

  • Principals: users (avoid long-lived keys), roles (assumed for temporary credentials) and AWS services.
  • Policies: JSON documents that Allow or Deny actions on resources. An explicit deny always wins.
  • Least privilege: grant only the actions and resources a workload needs.
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::my-app-artifacts/*"
  }]
}

Workloads should never use access keys. EC2 gets an instance profile, EKS pods use EKS Pod Identity or IRSA, Lambda gets an execution role, and CI uses OIDC federation (e.g. GitHub Actions assuming a role).

A standard VPC design

VPC 10.0.0.0/16
├── AZ a
│   ├── public  10.0.0.0/24   → ALB, NAT Gateway        (route 0.0.0.0/0 → Internet Gateway)
│   └── private 10.0.10.0/24  → app instances / EKS nodes (route 0.0.0.0/0 → NAT Gateway)
├── AZ b
│   ├── public  10.0.1.0/24
│   └── private 10.0.11.0/24
└── data subnets (no internet route) → RDS, ElastiCache
  • Only load balancers (and NAT) live in public subnets. Everything else is private.
  • Security groups can reference each other. For example, "the DB accepts 5432 only from the app's security group". That beats IP ranges.
  • VPC endpoints for S3, ECR and others keep traffic private and cut NAT data-processing charges.

The AWS CLI in 2 minutes

aws configure sso                       # log in via IAM Identity Center
aws sts get-caller-identity             # who am I right now?
aws s3 ls s3://my-bucket/ --recursive --human-readable
aws s3 sync ./dist s3://my-site-bucket --delete
aws ec2 describe-instances \
  --filters "Name=tag:env,Values=prod" \
  --query "Reservations[].Instances[].[InstanceId,State.Name,PrivateIpAddress]" \
  --output table
aws logs tail /aws/lambda/my-fn --follow
aws ecr get-login-password | docker login --username AWS --password-stdin <acct>.dkr.ecr.<region>.amazonaws.com
aws eks update-kubeconfig --name my-cluster --region eu-west-1

Cost habits that matter

  • Tag everything (env, team, service) and enable cost allocation tags, so Cost Explorer can tell you who spends what.
  • Watch the usual surprises: NAT Gateway hourly and per-GB charges, idle load balancers, unattached EBS volumes, old snapshots, and cross-AZ data transfer.
  • Right-size with Compute Optimizer, prefer Graviton (ARM) instances, buy Savings Plans for steady load, and use Spot for interruptible work.
  • Shut dev environments down at night. Better still, make them disposable with Terraform.

Security baseline checklist

  • Root MFA on, root keys deleted, SSO for humans
  • CloudTrail on in all regions, logging to a locked-down bucket
  • S3 Block Public Access enabled at the account level
  • GuardDuty and Security Hub on; AWS Config for drift and compliance
  • Encryption at rest everywhere (EBS, S3, RDS default encryption)
  • Multiple accounts (dev / prod / security) under AWS Organizations, with SCP guardrails
