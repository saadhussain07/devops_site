Security shouldn't be an afterthought reviewed at the end of a release cycle. Shifting left means integrating security checks into every stage of your CI/CD pipeline — automatically, on every commit.

Four Layers of Pipeline Security

  • SAST — Static Application Security Testing (source code analysis)
  • Dependency scanning — Check third-party libraries for known CVEs
  • Container scanning — Scan Docker images for vulnerabilities
  • Secrets detection — Find accidentally committed credentials

Complete Security Pipeline

name: Security Pipeline

on: [push, pull_request]

jobs:
  sast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run Semgrep SAST
        run: |
          pip install semgrep
          semgrep scan --config p/owasp-top-ten --error

  dependency-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Dependency audit
        run: npm audit --audit-level=high

  container-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t myapp:test .
      - name: Trivy container scan
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: myapp:test
          severity: HIGH,CRITICAL
          exit-code: 1

  secrets-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: GitLeaks secrets scan
        uses: gitleaks/gitleaks-action@v2

Golden rule: Set exit-code: 1 on CRITICAL findings so the pipeline fails and blocks the merge. Security gates only work if they're enforced.

Scan your infrastructure code too

Misconfigured Terraform, Kubernetes manifests and Dockerfiles cause more cloud breaches than exotic exploits. Scan them in the same pipeline:

  iac-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Trivy config scan
        uses: aquasecurity/trivy-action@0.28.0
        with:
          scan-type: config
          scan-ref: .
          severity: HIGH,CRITICAL
          exit-code: 1

Typical findings: security groups open to 0.0.0.0/0, unencrypted S3 buckets or EBS volumes, containers running as root, and missing resource limits.

Generate an SBOM and sign your images

A Software Bill of Materials lists every component in an image, so when the next big CVE lands you can answer "are we affected?" in seconds. Signing proves an image came from your pipeline and wasn't tampered with.

  sign:
    needs: container-scan
    runs-on: ubuntu-latest
    permissions:
      id-token: write          # keyless signing via OIDC
      packages: write
    steps:
      - uses: sigstore/cosign-installer@v3
      - uses: anchore/sbom-action@v0
        with:
          image: ghcr.io/you/app:${{ github.sha }}
          format: spdx-json
          output-file: sbom.spdx.json
      - run: |
          cosign sign --yes ghcr.io/you/app:${{ github.sha }}
          cosign attest --yes --predicate sbom.spdx.json --type spdxjson ghcr.io/you/app:${{ github.sha }}

In the cluster, a policy engine such as Kyverno can reject any image that isn't signed by your pipeline.

Keep dependencies patched automatically

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: docker
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }

Make it stick

  • Start in report-only mode, fix the backlog, then switch the gates to blocking. Teams disable noisy gates that block everything on day one.
  • Pin third-party actions to a version or a commit SHA, not @master.
  • Give the workflow least-privilege permissions: and use OIDC instead of long-lived cloud keys.
  • Turn on GitHub secret scanning and push protection so secrets are blocked before they land.
