When an alert fires at 3am, the first fifteen minutes usually go on gathering context: which pods are failing, what the logs say, what changed. An LLM agent can do that gathering in seconds and hand the on-call engineer a summary with evidence. This tutorial builds one in about 100 lines of Python, with one firm rule: the agent can look, but it can't touch.

What you'll build: Alertmanager sends a firing alert, and the agent queries Prometheus, Kubernetes events and pod logs. It then posts a triage report to Slack (summary, evidence, likely cause, suggested commands, confidence) and never changes the cluster.

Why read-only first?

Letting an AI run kubectl delete in production is a big step, and you shouldn't take it until you know how often its diagnosis is right. A read-only agent is safe to run from day one, and it still saves most of the time: in a typical incident, deciding what to do is quick once someone has collected the evidence. Measure the agent's accuracy for a few weeks, then consider one guarded action (see the guardrails checklist).

Architecture

Prometheus ──► Alertmanager ──webhook──► triage agent ──► Slack
                                             │
                     read-only tools ◄───────┘
                     • query_prometheus(promql)
                     • get_k8s_events(namespace)
                     • get_pod_logs(namespace, pod, previous)

The LLM decides which tools to call and in what order. Your code decides what each tool is allowed to do. That split is the core of a safe agent: the model chooses, your code enforces.

Prerequisites

  • A Kubernetes cluster with kube-prometheus-stack; the AIOps lab and Project 06 set this up locally with kind
  • Python 3.10+ and pip install anthropic requests
  • An Anthropic API key in ANTHROPIC_API_KEY
  • kubectl configured with a read-only service account (next step)

Step 1: A read-only identity

Give the agent its own service account that can read pods, logs, events and deployments, and nothing else. Leave Secrets out, because logs and manifests already reveal plenty.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: aiops-agent
  namespace: aiops
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: aiops-readonly
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log", "events", "services", "nodes"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: aiops-readonly
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: aiops-readonly
subjects:
  - kind: ServiceAccount
    name: aiops-agent
    namespace: aiops

Check that it really can't write: kubectl auth can-i delete pods --as=system:serviceaccount:aiops:aiops-agent should print no.

Step 2: The agent

The code uses the Anthropic Python SDK's tool runner. You write each tool as a normal Python function with a docstring, and the SDK turns it into a tool definition. It then runs the loop: the model asks for a tool, the SDK calls your function, sends back the result, and repeats until the model writes its final answer.

"""Read-only Kubernetes incident triage agent.

The model can only *look* (PromQL queries, events, logs). It never changes
the cluster: it writes a triage report and suggests commands for a human.
"""
import json
import os
import re
import subprocess

import anthropic
import requests
from anthropic import beta_tool

PROM_URL = os.environ.get("PROM_URL", "http://localhost:9090")
ALLOWED_NAMESPACES = {"app", "payments"}        # the agent may only look here
POD_NAME = re.compile(r"^[a-z0-9]([-a-z0-9.]*[a-z0-9])?$")
MAX_OUTPUT = 8000                                # keep tool results small


def _kubectl(*args: str) -> str:
    # List form (no shell), so arguments can't be used for injection.
    out = subprocess.run(["kubectl", *args], capture_output=True, text=True, timeout=20)
    return (out.stdout or out.stderr)[-MAX_OUTPUT:]


@beta_tool
def query_prometheus(promql: str) -> str:
    """Run an instant PromQL query and return up to 20 series as JSON.

    Args:
        promql: A PromQL expression, e.g. sum(rate(http_requests_total{code=~"5.."}[5m])) by (service)
    """
    r = requests.get(f"{PROM_URL}/api/v1/query", params={"query": promql}, timeout=10)
    if r.status_code != 200:
        return f"error: Prometheus returned {r.status_code}: {r.text[:500]}"
    return json.dumps(r.json()["data"]["result"][:20])


@beta_tool
def get_k8s_events(namespace: str) -> str:
    """List recent Kubernetes events in a namespace, newest last.

    Args:
        namespace: Kubernetes namespace to inspect.
    """
    if namespace not in ALLOWED_NAMESPACES:
        return f"error: namespace '{namespace}' is not allowed"
    return _kubectl("get", "events", "-n", namespace, "--sort-by=.lastTimestamp")


@beta_tool
def get_pod_logs(namespace: str, pod: str, previous: bool = False) -> str:
    """Return the last 200 log lines of a pod.

    Args:
        namespace: Kubernetes namespace of the pod.
        pod: Pod name.
        previous: True to read the logs of the previous (crashed) container.
    """
    if namespace not in ALLOWED_NAMESPACES:
        return f"error: namespace '{namespace}' is not allowed"
    if not POD_NAME.match(pod):
        return "error: invalid pod name"
    args = ["logs", pod, "-n", namespace, "--tail=200"]
    if previous:
        args.append("--previous")
    return _kubectl(*args)


SYSTEM = """You are an SRE triage assistant for a Kubernetes platform.
You can only read data: PromQL queries, Kubernetes events and pod logs.
Investigate the alert, then reply with exactly these sections:
Summary, Evidence (the queries/logs you relied on), Likely cause,
Suggested next steps (commands for a human to run), Confidence (low/medium/high).
If the evidence is inconclusive, say so instead of guessing."""

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY


def triage(alert: dict) -> str:
    runner = client.beta.messages.tool_runner(
        model="claude-opus-5-5",
        max_tokens=16000,
        output_config={"effort": "medium"},
        # If the model declines, retry automatically on a fallback model.
        betas=["server-side-fallback-2026-07-01"],
        fallbacks="default",
        max_iterations=10,
        system=SYSTEM,
        tools=[query_prometheus, get_k8s_events, get_pod_logs],
        messages=[{
            "role": "user",
            "content": "Investigate this alert:\n" + json.dumps(alert, indent=2),
        }],
    )
    final = runner.until_done()
    if final.stop_reason == "refusal":
        return "The model declined this request; triage it manually."
    return "".join(block.text for block in final.content if block.type == "text")


if __name__ == "__main__":
    example_alert = {
        "alertname": "KubePodCrashLooping",
        "namespace": "payments",
        "pod": "payments-api-7d9f8b6c5-x2kqz",
        "severity": "page",
    }
    print(triage(example_alert))

How the guardrails work

  • Namespace allowlist: the model can ask about any namespace, but the tools only answer for the ones you list.
  • Input validation: pod names must match the Kubernetes naming pattern, so a value like --all-containers can't slip in as a flag.
  • No shell: subprocess.run gets a list of arguments, so nothing is interpreted by a shell.
  • Small outputs: results are trimmed (20 series, 200 log lines, 8,000 characters), which keeps the model focused and the cost predictable.
  • Iteration cap: max_iterations=10 stops a confused agent from looping forever.
  • Refusal fallback: fallbacks="default" retries on another model if the first one declines, and the code checks stop_reason before using the answer.

Treat logs as untrusted input. A log line can contain text written to manipulate an AI ("ignore previous instructions…"). That's why the tools enforce limits in code rather than trusting the model to stay inside them. Even a fully tricked agent can only read.

Step 3: Connect it to Alertmanager

A small web server receives Alertmanager's webhook. It replies right away, runs the investigation in the background, and posts the report to Slack.

"""Receive Alertmanager webhooks, triage firing alerts, post reports to Slack."""
import json
import os
from concurrent.futures import ThreadPoolExecutor
from http.server import BaseHTTPRequestHandler, HTTPServer

import requests

from triage_agent import triage

SLACK_WEBHOOK_URL = os.environ["SLACK_WEBHOOK_URL"]
pool = ThreadPoolExecutor(max_workers=2)   # at most 2 investigations at once


def investigate(alert: dict) -> None:
    report = triage(alert)
    title = alert.get("alertname", "alert")
    requests.post(SLACK_WEBHOOK_URL, json={"text": f"*AI triage: {title}*\n{report}"}, timeout=10)


class AlertHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        payload = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        for alert in payload.get("alerts", []):
            if alert.get("status") == "firing":
                pool.submit(investigate, {**alert.get("labels", {}), **alert.get("annotations", {})})
        # Answer straight away; the investigation runs in the background.
        self.send_response(202)
        self.end_headers()


if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 8080), AlertHandler).serve_forever()

Then add a route in your Alertmanager config, so paging alerts go to the agent as well as to your normal receiver:

route:
  receiver: default
  routes:
    - matchers: [severity="page"]
      receiver: aiops-agent
      continue: true          # keep normal notifications too
receivers:
  - name: aiops-agent
    webhook_configs:
      - url: http://aiops-agent.aiops.svc:8080/alert

Step 4: Test it with real faults

Break your lab cluster on purpose and read each report:

kubectl -n payments set image deploy/api api=ghcr.io/you/api:does-not-exist   # ImagePullBackOff
kubectl -n payments set resources deploy/api --limits=memory=16Mi             # OOMKilled
kubectl -n payments scale deploy/db --replicas=0                              # dependency down

For each one, score the report: was the likely cause right? Did it cite real evidence? Did it say "inconclusive" when it should have? Keep the scores in a spreadsheet. That number tells you whether the agent is ready for more responsibility.

Cost and privacy

  • Cost: each investigation is a handful of API calls with small tool results. Only route severity="page" alerts to the agent, and cap concurrency (the webhook runs at most two at once).
  • Data: logs and metrics are sent to the model provider. Don't send logs that contain personal data or secrets, and check what your company's policy allows before using production data.
