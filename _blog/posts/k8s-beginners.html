Kubernetes (K8s) is the de facto standard for running containerised applications at scale. It automates deployment, scaling, and management of containers across a cluster of machines. Here's what every beginner needs to know.

Core Objects

Pod — The Smallest Unit

A Pod is the smallest deployable unit in Kubernetes. It wraps one or more containers that share network and storage.

apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  containers:
  - name: app
    image: nginx:alpine
    ports:
    - containerPort: 80

Deployment — Managing Replicas

You almost never create Pods directly. Use a Deployment to manage multiple replicas with rolling updates and rollbacks.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: myapp:1.0
        resources:
          requests:
            memory: "64Mi"
            cpu: "250m"
          limits:
            memory: "128Mi"
            cpu: "500m"

Service — Networking

A Service exposes your Pods via a stable DNS name and IP address, load balancing across all healthy Pods.

apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP

Essential kubectl Commands

# Apply manifest
kubectl apply -f deployment.yaml

# Get resources
kubectl get pods
kubectl get deployments
kubectl get services

# Describe a resource
kubectl describe pod my-app-abc123

# View logs
kubectl logs my-app-abc123 -f

# Execute into a container
kubectl exec -it my-app-abc123 -- /bin/sh

# Scale a deployment
kubectl scale deployment my-app --replicas=5

# Rolling update
kubectl set image deployment/my-app app=myapp:2.0

# Rollback
kubectl rollout undo deployment/my-app

Practice tip: Use kind or minikube to run a local Kubernetes cluster on your laptop for free. No cloud account needed.

Run it locally with kind

# install kind (https://kind.sigs.k8s.io) and kubectl, then:
kind create cluster --name lab
kubectl cluster-info --context kind-lab
kubectl get nodes

# load a locally built image into the cluster (no registry needed)
docker build -t myapp:1.0 .
kind load docker-image myapp:1.0 --name lab

Namespaces

Namespaces split one cluster into virtual sub-clusters, such as per team or per environment. Most resources (Pods, Deployments, Services, Secrets) are namespaced; nodes and PersistentVolumes are not.

kubectl create namespace dev
kubectl -n dev get all
kubectl config set-context --current --namespace=dev   # change your default

Configuration: ConfigMaps and Secrets

Keep configuration out of the image so the same image runs in every environment.

apiVersion: v1
kind: ConfigMap
metadata:
  name: my-app-config
data:
  LOG_LEVEL: info
  FEATURE_X: "true"
---
apiVersion: v1
kind: Secret
metadata:
  name: my-app-secret
type: Opaque
stringData:
  DATABASE_URL: postgres://app:change-me@db:5432/app

Use them in the Deployment's container spec:

        envFrom:
        - configMapRef:
            name: my-app-config
        - secretRef:
            name: my-app-secret

Secrets are only base64-encoded, not encrypted. Don't commit them to Git. Use External Secrets, Sealed Secrets or SOPS (see GitOps with Argo CD).

Health checks: readiness and liveness probes

        readinessProbe:          # gate traffic until the app is ready
          httpGet: { path: /ready, port: 8080 }
          periodSeconds: 5
        livenessProbe:           # restart the container if it hangs
          httpGet: { path: /healthz, port: 8080 }
          initialDelaySeconds: 10
          periodSeconds: 10

Without a readiness probe, a rolling update sends traffic to pods before they can serve it. Keep the liveness probe simple: it should check the process itself, not the database.

Exposing HTTP with an Ingress

A Service of type LoadBalancer per app gets expensive. An Ingress routes many hostnames and paths through one load balancer, via an Ingress controller such as ingress-nginx or Traefik. The newer Gateway API is its successor and works the same way.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app
spec:
  ingressClassName: nginx
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: my-app-service
            port:
              number: 80

Debugging workflow

kubectl get pods                          # STATUS and RESTARTS
kubectl describe pod <pod>                # the Events section explains most failures
kubectl logs <pod> --previous             # logs from the last crash
kubectl get events --sort-by=.lastTimestamp
kubectl port-forward svc/my-app-service 8080:80   # test a Service from your laptop
