    What is AIOps?

    AIOps (Artificial Intelligence for IT Operations) applies AI and ML to automate and enhance IT operations — turning massive volumes of telemetry data into actionable intelligence. It's the evolution from humans watching dashboards to systems that watch, reason, and fix themselves.

    👁️
    2000s
    Reactive Monitoring
    Humans watch dashboards. Alerts fire. Teams scramble. Mean time to detect: hours.
    📊
    2010s
    Predictive Analytics
    ML models learn normal behaviour and warn before thresholds are crossed.
    ⚡
    2020s
    Intelligent Correlation
    AI correlates metrics, logs, traces across thousands of services simultaneously.
    🤖
    Now
    Autonomous Operations
    LLM agents detect, diagnose, and remediate faults without human intervention.

    The AIOps Maturity Model

    AIOps isn't a product you install. It's a set of capabilities you add one level at a time. Skipping levels is the most common reason AIOps projects fail: an AI can't reason about telemetry you don't collect or alerts nobody trusts.

    Level 0
    Reactive

    What it looks like

    Users report outages before the team notices. Debugging means SSH-ing into servers and grepping logs.

    Next step

    Collect metrics and centralise logs. Add uptime checks for every user-facing endpoint.

    Level 1
    Monitored

    What it looks like

    Dashboards and static-threshold alerts (CPU > 80%). Lots of noisy pages; some real issues still slip through.

    Next step

    Define SLOs and alert on symptoms users feel (error rate, latency), not every resource metric.

    Level 2
    Correlated

    What it looks like

    SLO burn-rate alerts, alerts grouped and de-duplicated, every alert linked to a runbook and enriched with recent deploys.

    Next step

    Add dynamic baselines for metrics with daily or weekly patterns, and connect metrics, logs and traces.

    Level 3
    AI-assisted

    What it looks like

    Anomaly detection catches what thresholds miss. An LLM agent gathers context when an alert fires and posts a triage summary. Humans decide and act.

    Next step

    Measure how often the suggested cause is right. Automate only fixes that are well understood and reversible.

    Level 4
    Guarded autonomy

    What it looks like

    Known, low-risk fixes (restart, rollback, scale out) run automatically within policy limits, with an audit trail, a kill switch and post-fix verification.

    Keep improving

    Review every automated action in postmortems. Widen the allowed actions slowly, and only with evidence.

    Core AIOps Techniques

    Most AIOps value comes from a handful of techniques, and many work with the Prometheus and Alertmanager you already run, no ML platform required.

    📉 Dynamic baselines (z-score)

    Instead of a fixed threshold, compare a metric to its own recent history. A z-score above 3 means "much higher than usual for this service".

    # how unusual is the current request rate? ( rate(http_requests_total[5m]) - avg_over_time(rate(http_requests_total[5m])[1d:5m]) ) / stddev_over_time(rate(http_requests_total[5m])[1d:5m])

    📅 Seasonality

    Traffic at 9am Monday looks nothing like 3am Sunday. Compare against the same time last week to cut false alarms on predictable peaks.

    # current traffic vs the same time 1 week ago sum(rate(http_requests_total[5m])) / sum(rate(http_requests_total[5m] offset 1w))

    🔮 Forecasting

    Predict problems before they happen. A linear forecast catches a disk that will fill up hours before any threshold alert would fire.

    # disk predicted to run out within 4 hours predict_linear( node_filesystem_avail_bytes{fstype!="tmpfs"}[6h], 4 * 3600 ) < 0

    🧩 Alert correlation & noise reduction

    One failing database can trigger fifty alerts. Group related alerts into one notification, and suppress symptoms when the cause is already firing.

    # alertmanager.yml route: group_by: [alertname, namespace, service] group_wait: 30s inhibit_rules: - source_matchers: [alertname="NodeDown"] target_matchers: [severity="warning"] equal: [node]

    🔍 Change correlation for root cause

    Most incidents follow a change. Lining up alert start times with deploys, config changes and feature flags is the cheapest root-cause signal there is.

    # what changed recently in this namespace? kubectl -n payments rollout history deploy/api kubectl -n payments get events \ --sort-by=.lastTimestamp | tail -20

    🤖 LLM-assisted triage

    An LLM agent with read-only tools gathers metrics, events and logs when an alert fires, then writes a summary with evidence and a likely cause, so the on-call engineer starts with context.

    # tools the agent may call (read-only) query_prometheus(promql) get_k8s_events(namespace) get_pod_logs(namespace, pod, previous)

    How LLM Agents Understand Kubernetes

    🧠

    Natural Language Reasoning

    LLMs understand Kubernetes YAML manifests, event logs, and error messages in natural language — no rigid rule engines or decision trees. They reason about failure modes the way a senior SRE would.

    📡

    Context-Aware Analysis

    Agents correlate signals across kubectl describe, Prometheus alerts, and Loki logs simultaneously — understanding the full context before acting. No more siloed tooling.

    ⚡

    Faster First Response

    An agent can gather metrics, events and logs the moment an alert fires, so the on-call engineer starts with context instead of a blank terminal. Less time spent searching means a shorter MTTR and less SLO budget burned.

    🔒

    Safe Action Guardrails

    Agents operate within defined RBAC boundaries. Every remediation action is validated against a policy engine before execution — preventing hallucination-driven catastrophes in production.

    📖

    Runbook Augmentation

    LLMs generate and execute runbook steps dynamically based on the specific failure context — not just matching predefined templates. Each incident becomes a learning opportunity.

    🔁

    Continuous Learning Loop

    Feed postmortems back in: turn each incident's findings into better runbooks, alert rules and prompts, and track false positives and misses so the system's suggestions improve over time.

    Prometheus · Loki · Jaeger

    The three pillars of the observability stack — each feeding a different signal type to the AIOps agent pipeline for complete situational awareness.

    📊

    Prometheus

    Metrics — The "What"

    Prometheus scrapes time-series metrics from every Kubernetes component — CPU, memory, request rates, error rates, latency. The Fault Detection Agent uses PromQL queries to identify statistical anomalies in real time.

    • RED metrics: Rate, Errors, Duration per service
    • kube-state-metrics for cluster health signals
    • Custom metrics from application /metrics endpoints
    • Alertmanager fires structured alerts to agent pipeline
    📋

    Grafana Loki

    Logs — The "Why"

    Loki aggregates structured logs from all pods and system components. The RCA Agent uses LogQL to query log streams around the time of a detected anomaly — extracting the root cause from stack traces, error messages, and audit logs.

    • Label-based log indexing (low storage overhead)
    • LogQL for contextual log correlation
    • Promtail agent for pod log collection
    • LLM parses unstructured log text naturally
    🔀

    Jaeger

    Traces — The "Where"

    Jaeger captures end-to-end request traces across microservices. When a fault occurs, the RCA Agent queries trace data to pinpoint exactly which service, span, or dependency introduced the latency or error — in milliseconds.

    • OpenTelemetry SDK instrumentation
    • Service dependency graph generation
    • Span-level error attribution
    • Cascading failure path visualisation

    5 Faults Every AIOps System Should Handle

    Use these as test cases for your own lab: inject each fault, check that it's detected, and compare the agent's diagnosis with the real cause. Each card shows the signal to watch and the safe fix.

    Scenario 01
    💥
    Pod Crash Loop
    Signal: kube_pod_container_status_restarts_total rising, CrashLoopBackOff events. Check the previous container's logs first.
    Safe fix: roll back the last change
    Scenario 02
    🔥
    CPU Saturation
    Signal: CPU throttling (container_cpu_cfs_throttled_periods_total) and rising p95 latency together.
    Safe fix: scale out within HPA limits
    Scenario 03
    💾
    Memory Leak (OOMKill)
    Signal: working-set memory climbing steadily toward the limit, then restarts with reason OOMKilled (exit 137).
    Safe fix: restart now, ticket the leak
    Scenario 04
    🌐
    Dependency Failure
    Signal: error rate up on several services at once, traces all failing at the same downstream call.
    Safe fix: page the owner of the dependency
    Scenario 05
    📦
    Bad Deployment
    Signal: errors or latency jump right after a rollout, while the previous version was healthy.
    Safe fix: automatic rollback

    Build Your Own AIOps Lab

    Six steps from an empty laptop to an AI agent that triages real alerts on a local Kubernetes cluster. Everything runs locally except the LLM API calls.

    Create a cluster with observability

    Start a kind cluster, install kube-prometheus-stack and Loki, and deploy a sample app. Projects 05 and 06 walk through this.

    kind create cluster --name aiops helm upgrade --install monitoring prometheus-community/kube-prometheus-stack \ -n monitoring --create-namespace

    Give the agent a read-only identity

    The agent's service account can read pods, logs, events and deployments, and nothing else: no writes, and no Secrets.

    apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: aiops-readonly rules: - apiGroups: [""] resources: ["pods", "pods/log", "events", "services", "nodes"] verbs: ["get", "list", "watch"] - apiGroups: ["apps"] resources: ["deployments", "replicasets"] verbs: ["get", "list", "watch"]

    Write the triage agent

    A short Python program gives an LLM three read-only tools (PromQL queries, events, pod logs) and asks it for a structured report: summary, evidence, likely cause, next steps and confidence.

    Full, tested code: Build a Read-Only LLM Triage Agent for Kubernetes →

    Send alerts to the agent

    Route paging alerts to the agent through an Alertmanager webhook, and post its report to Slack or the incident channel. continue: true keeps your normal notifications working too.

    route: receiver: default routes: - matchers: [severity="page"] receiver: aiops-agent continue: true receivers: - name: aiops-agent webhook_configs: - url: http://aiops-agent.aiops.svc:8080/alert

    Break things on purpose

    Inject the five faults above and grade each report: did the agent find the real cause? Did it admit when it wasn't sure? Keep a simple scorecard.

    kubectl -n app set image deploy/api api=ghcr.io/you/api:does-not-exist # bad deploy kubectl -n app set resources deploy/api --limits=memory=16Mi # OOMKilled kubectl -n app scale deploy/db --replicas=0 # dependency down

    Only then, add one guarded action

    Once the diagnoses are reliably right, allow a single reversible action, such as kubectl rollout undo for the deployment named in the alert. Require a human to approve it in Slack, and verify the SLIs recover afterwards.

    Guardrails Before AI Touches Production

    An AI agent that can change production is a new kind of operator. Hold it to the same standards as a human with production access, and stricter ones where it's cheap to do so.

    • Read-only by default. Investigation needs no write access. Grant writes one narrow action at a time.
    • Its own identity. A dedicated service account and cloud role, never a human's credentials or cluster-admin.
    • Allowlisted actions. "Restart deployment X in namespace Y", not a shell. Validate every argument before running it.
    • Human approval for changes. Show the evidence and the exact command, and wait for a person to approve.
    • Blast-radius limits. Cap how many actions it can take per hour, and never act on more than one service at a time.
    • Audit everything. Log every tool call, input, output and decision, so you can review them in postmortems.
    • Kill switch. One flag that turns all automated actions off instantly.
    • Treat telemetry as untrusted. Log lines and alert text can contain prompt-injection attempts. Never let them grant the agent new permissions.
    • Verify after acting. Check that the SLIs recovered, and roll back the agent's own change if they didn't.
