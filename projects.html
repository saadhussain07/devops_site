      01

      Linux Server Health & Backup Automation

      Write Bash scripts that check disk, memory and service health, rotate logs and back up a directory on a schedule.

      Beginner ~1 weekend BashcronsystemdSSH
      What you'll learn
      • Writing safe Bash: set -euo pipefail, functions, exit codes and arguments
      • Reading system state with df, free, systemctl and journalctl
      • Scheduling with cron and systemd timers, and understanding the difference
      • Key-based SSH and copying backups to a second machine with rsync
      Steps
      1. Get a Linux box. Use a local VM (Multipass, VirtualBox or WSL2) or a free-tier cloud instance.
      2. Write healthcheck.sh. Warn when disk usage is above 80% or free memory is below 10%, and when a named service (e.g. nginx) is not active. Exit non-zero on any failure.
      3. Write backup.sh. Tar and gzip a directory with a timestamp, keep the last 7 archives and delete older ones.
      4. Schedule both. Run the health check every 5 minutes with cron, and the backup nightly with a systemd timer.
      5. Ship backups off-box. Set up SSH keys and rsync the archive to a second VM or an S3 bucket.
      6. Lint. Run shellcheck on every script and fix all warnings.
      #!/usr/bin/env bash
set -euo pipefail

THRESHOLD=${THRESHOLD:-80}
status=0

while read -r use mount; do
  pct=${use%\%}
  if (( pct > THRESHOLD )); then
    echo "WARN: $mount is ${pct}% full"
    status=1
  fi
done < <(df -h --output=pcent,target -x tmpfs -x devtmpfs | tail -n +2)

for svc in "$@"; do
  systemctl is-active --quiet "$svc" || { echo "FAIL: $svc is not running"; status=1; }
done

exit "$status"
      Done when
      • shellcheck *.sh reports nothing
      • Stopping the service makes the health check exit with code 1
      • systemctl list-timers shows your backup timer, and only 7 archives exist after a week
      Stretch goals & résumé bullet
      • Send failures to a Slack or Discord webhook with curl
      • Package the scripts as an Ansible role so you can deploy them to any server

      "Automated server health monitoring and 7-day rotating backups with Bash, cron and systemd timers, with off-host replication over SSH."

      Containerise a 3-Tier App with Docker Compose

      Package a web frontend, an API and a PostgreSQL database into containers and run the whole stack with one command.

      Beginner ~1 weekend DockerComposePostgreSQLNginx
      Architecture
      browser → nginx (frontend, :80) → api (:8000) → postgres (:5432, named volume)

      Use any small API you like (Flask, FastAPI, Express or Go). A to-do list with create, list and delete endpoints is enough.

      Steps
      1. Write a multi-stage Dockerfile for the API, so the final image has no compilers or dev dependencies.
      2. Run as non-root and add a HEALTHCHECK.
      3. Serve the frontend from an nginx:alpine image that proxies /api to the API container.
      4. Write compose.yaml with a named volume for Postgres, a .env file for secrets and depends_on with condition: service_healthy.
      5. Measure. Compare image sizes before and after multi-stage builds and record the numbers in your README.
      services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5
  api:
    build: ./api
    environment:
      DATABASE_URL: postgres://postgres:${DB_PASSWORD}@db:5432/postgres
    depends_on:
      db: { condition: service_healthy }
  web:
    build: ./web
    ports: ["8080:80"]
    depends_on: [api]
volumes:
  pgdata:
      Done when
      • docker compose up -d on a fresh clone gives a working app at localhost:8080
      • Data survives docker compose down && docker compose up -d
      • The API image is under 150 MB and docker compose exec api whoami is not root
      Stretch goals & résumé bullet
      • Scan your images with trivy image and fix HIGH/CRITICAL findings
      • Add a compose.override.yaml for hot reload during development

      "Containerised a 3-tier application with multi-stage Docker builds, cutting image size by X% and enabling one-command local environments with Docker Compose."

      CI/CD Pipeline with GitHub Actions

      Every pull request runs lint, tests and a security scan. Every merge to main builds and pushes a versioned image to a registry.

      Beginner ~1 week GitHub ActionsGHCRTrivy
      Architecture
      PR → lint → unit tests → docker build → trivy scan ✔ → merge → build → push ghcr.io/you/app:sha & :latest

      Reuse the API from Project 02.

      Steps
      1. Add tests to the API, even just 3–5, so the pipeline has something to run.
      2. Create .github/workflows/ci.yml that runs on pull_request and on push to main.
      3. Cache dependencies with the setup action's built-in cache.
      4. Scan the image with Trivy and fail the job on CRITICAL vulnerabilities.
      5. Push to GHCR using the built-in GITHUB_TOKEN, so no personal tokens are needed. Tag images with the commit SHA. Image names must be lowercase, so use a lowercase repo name or set the image name yourself.
      6. Protect main: require the CI check to pass before merging.
      name: ci
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r api/requirements.txt && pytest api
      - run: docker build -t ghcr.io/${{ github.repository }}:${{ github.sha }} api
      - uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: ghcr.io/${{ github.repository }}:${{ github.sha }}
          severity: CRITICAL
          exit-code: "1"
      - if: github.ref == 'refs/heads/main'
        run: |
          echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
          docker push ghcr.io/${{ github.repository }}:${{ github.sha }}
      Done when
      • A PR with a failing test cannot be merged
      • Merging to main produces a new image in your repo's Packages tab, tagged with the commit SHA
      • The README shows a passing CI status badge
      Stretch goals & résumé bullet
      • Add a matrix build across two language versions
      • Move the build logic into a reusable workflow and call it from a second repo
      • Generate an SBOM with Syft and attach it as a build artifact

      "Built a GitHub Actions pipeline with automated tests, container vulnerability scanning and SHA-tagged image publishing, gating every merge to main."

      Terraform an AWS Network & Web Tier

      Provision a VPC, public and private subnets, a load balancer and an auto-scaling group using reusable modules and remote state.

      Intermediate ~1–2 weeks TerraformAWSS3 stateIAM
      Architecture
      VPC 10.0.0.0/16 → 2 public subnets (ALB) + 2 private subnets (ASG of EC2 running your container) → NAT → internet

      ⚠ An ALB and a NAT gateway are not free. Expect a few dollars per day, so destroy everything when you finish each session. For a free variant, skip the NAT and put the instances in public subnets with tight security groups.

      Steps
      1. Bootstrap state. Create an S3 bucket (versioning on) for remote state, and enable S3 native locking with use_lockfile = true (Terraform 1.10+).
      2. Write a network module: VPC, subnets across 2 AZs, route tables, IGW and NAT.
      3. Write a web module: launch template whose user-data runs your Docker image, an ASG (min 2) and an ALB with a health-checked target group.
      4. Use environments. Create envs/dev and envs/prod folders that call the same modules with different variables.
      5. Add guardrails: terraform fmt -check, terraform validate and tflint in CI, with terraform plan output posted to PRs.
      terraform {
  required_version = ">= 1.10"
  backend "s3" {
    bucket       = "yourname-tfstate"
    key          = "dev/web/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
  }
}

module "network" {
  source   = "../../modules/network"
  cidr     = "10.0.0.0/16"
  az_count = 2
}

module "web" {
  source          = "../../modules/web"
  vpc_id          = module.network.vpc_id
  public_subnets  = module.network.public_subnet_ids
  private_subnets = module.network.private_subnet_ids
  image           = "ghcr.io/you/app:latest"
  min_size        = 2
}
      Done when
      • The ALB DNS name serves your app, and terminating an instance gets it replaced automatically
      • A second terraform plan reports No changes
      • terraform destroy removes everything cleanly
      Stretch goals & résumé bullet
      • Use GitHub OIDC to assume an AWS role from CI, with no long-lived access keys
      • Add HTTPS with ACM and a Route 53 record
      • Add checkov or trivy config to scan the Terraform code

      "Designed reusable Terraform modules for a multi-AZ AWS VPC and auto-scaling web tier behind an ALB, with S3 remote state and plan-on-PR CI."

      Deploy to Kubernetes with Helm

      Run the 3-tier app on a local Kubernetes cluster with a Helm chart, Ingress, probes, resource limits and autoscaling.

      Intermediate ~1–2 weeks KuberneteskindHelmIngressHPA
      Steps
      1. Create a cluster with kind (3 nodes) and install the ingress-nginx controller and metrics-server.
      2. Write raw manifests first: a Deployment and Service for the API and web, a StatefulSet and PVC for Postgres, and a Secret for the DB password.
      3. Add probes (readiness and liveness) and resource requests and limits to every container.
      4. Convert to a Helm chart with helm create, then move image tags, replicas and hostnames into values.yaml.
      5. Add an HPA on the API (CPU 70%), load-test with hey or k6, and watch it scale.
      6. Practise rollouts: deploy a broken image, watch the readiness probe stop it, then run helm rollback.
      kind create cluster --name lab --config kind.yaml
helm upgrade --install ingress-nginx ingress-nginx \
  --repo https://kubernetes.github.io/ingress-nginx -n ingress-nginx --create-namespace
helm upgrade --install app ./chart -n app --create-namespace \
  --set api.image.tag=$(git rev-parse --short HEAD)
kubectl -n app get pods,svc,ingress,hpa
kubectl -n app rollout status deploy/app-api
      Done when
      • helm install on a fresh cluster brings up a working app reachable through the Ingress
      • Deleting the Postgres pod loses no data
      • The HPA scales the API above 1 replica under load and back down afterwards
      • helm lint passes
      Stretch goals & résumé bullet
      • Add NetworkPolicies so only the API can reach Postgres
      • Replace the plain Secret with External Secrets or Sealed Secrets
      • Run the same chart on a managed cluster (EKS, GKE or AKS) using Project 04's Terraform skills

      "Packaged a multi-service application as a Helm chart with health probes, resource limits, Ingress and Horizontal Pod Autoscaling, validated under load."

      06

      Observability Stack: Metrics, Logs & Alerts

      Instrument your app, then collect metrics with Prometheus, logs with Loki, build Grafana dashboards and alert on SLOs.

      Intermediate ~1 week PrometheusGrafanaLokiAlertmanager
      Steps
      1. Install kube-prometheus-stack with Helm on your Project 05 cluster.
      2. Instrument the API with a Prometheus client library: request count, errors and a latency histogram (the RED method).
      3. Add a ServiceMonitor so Prometheus scrapes it automatically.
      4. Install Loki and Grafana Alloy to ship pod logs, then correlate a latency spike with the matching log lines in Grafana.
      5. Build a dashboard showing request rate, error %, p50/p95/p99 latency and pod CPU/memory. Export it as JSON into your repo.
      6. Define an SLO (e.g. 99.5% of requests succeed) and add a multi-window burn-rate alert as a PrometheusRule.
      # error ratio over 5 minutes
sum(rate(http_requests_total{job="api",code=~"5.."}[5m]))
  /
sum(rate(http_requests_total{job="api"}[5m]))

# p95 latency
histogram_quantile(0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m])))
      Done when
      • Your dashboard loads from the JSON in your repo
      • Injecting errors (e.g. an endpoint that returns 500) fires the alert within minutes
      • You can jump from a dashboard panel to the matching logs in one click
      Stretch goals & résumé bullet
      • Add distributed tracing with OpenTelemetry and Tempo or Jaeger
      • Route alerts to Slack and write a one-page runbook linked from the alert

      "Implemented RED-method metrics, centralised logging and SLO burn-rate alerting for a Kubernetes service using Prometheus, Loki and Grafana."

      GitOps Delivery with Argo CD

      Make Git the single source of truth. CI builds images, updates a config repo, and Argo CD syncs every environment automatically.

      Advanced ~2 weeks Argo CDKustomize/HelmGitHub Actions
      Architecture
      app repo → CI builds ghcr.io/app:sha → PR bumps tag in gitops repo → merge → Argo CD syncs dev → promote PR → prod
      Steps
      1. Split repos: app code in one repo, and environment config (envs/dev, envs/prod) in a gitops repo.
      2. Install Argo CD and create one Application per environment. Use the app-of-apps pattern or an ApplicationSet.
      3. Enable automated sync with prune and selfHeal for dev, and manual sync for prod.
      4. Extend Project 03's CI to open a PR against the gitops repo that bumps the image tag.
      5. Test drift: kubectl scale a deployment by hand and watch Argo CD revert it.
      6. Roll back by reverting the Git commit, not with kubectl.
      apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: app-dev
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/you/gitops
    targetRevision: main
    path: envs/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: app-dev
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [CreateNamespace=true]
      Done when
      • A code merge reaches dev with no manual kubectl or helm commands
      • Manual changes in the cluster are reverted automatically
      • Promoting to prod is a reviewed pull request
      Stretch goals & résumé bullet
      • Add canary releases with Argo Rollouts and automated analysis against your Project 06 Prometheus metrics
      • Send Argo CD notifications to Slack

      "Implemented GitOps continuous delivery with Argo CD across dev and prod, with automated drift correction and Git-based promotion and rollback."

      08

      Capstone: Secure Production Platform on EKS

      Combine everything: Terraform-built EKS, GitOps delivery, observability, secrets management, policy enforcement and a written incident drill.

      Advanced ~3–4 weeks EKSTerraformArgo CDKyvernoExternal Secrets
      Scope
      1. Infrastructure: Terraform the VPC and EKS cluster (managed node group or Karpenter), with an ECR repo and OIDC roles for CI.
      2. Bootstrap: Terraform installs Argo CD only. Argo CD then installs everything else (ingress, cert-manager, monitoring, External Secrets, Kyverno) from Git.
      3. Security: pull secrets from AWS Secrets Manager via External Secrets. Kyverno policies block :latest tags, privileged pods and images from unknown registries.
      4. Delivery: CI from Project 03, plus image signing with Cosign and signature verification in the cluster.
      5. Reliability: SLO dashboards and alerts from Project 06, a PodDisruptionBudget, and topology spread across AZs.
      6. Game day: kill a node, break a deployment and fill a disk. Write a blameless postmortem for one incident.
      Done when
      • terraform apply followed by an Argo CD sync recreates the whole platform from nothing
      • An unsigned image or a privileged pod is rejected at admission
      • The repo contains an architecture diagram, a cost estimate, runbooks and one postmortem
      Cost warning & résumé bullet

      ⚠ The EKS control plane costs about $0.10/hour, plus nodes and NAT. Build and test in short sessions, then destroy. Set an AWS Budget alert before you start.

      "Built a production-style Kubernetes platform on AWS EKS with Terraform and Argo CD, enforcing supply-chain security (Cosign, Kyverno) and SLO-based alerting, validated through chaos game days."
